# 科研写作与论文调研助手：产品需求文档

> 版本：v1.0  
> 更新日期：2026-08-28  
> 产品阶段：从可运行 MVP 演进为本地优先的个人科研工作台

## 1. 产品定义

本产品是一套面向中文计算机科研用户的论文助手。它不以“替用户凭记忆写一篇看似合理的文本”为目标，而是帮助用户完成可复查、可持续积累的科研工作闭环：

```text
提出研究问题
  -> 可信检索与筛选
  -> 保存个人文献资产
  -> 阅读全文并提取证据
  -> 组织观点、撰写与修订
  -> 导出、追溯与持续更新
```

产品的三个并列核心为：

1. **可信检索**：根据真实研究主题检索、筛选、去重和排序多源论文，避免编造论文和不相关召回。
2. **深度阅读**：读取上传或本地保存的 PDF，定位摘要、方法、实验、结论及其原文位置。
3. **证据化写作**：生成或改写各种学术写作交付物；每个外部事实、观点和引用均能回到真实论文记录或全文证据。

`Related Work` 是重要交付物，但不是产品中心的全部。系统必须支持从单篇论文解读、文献综述、研究报告，到论文各章节草稿、修订和导出的完整写作流程。

## 2. 产品定位与竞争策略

通用大模型、SciSpace、Elicit、Consensus、ResearchRabbit、scite、Paperpal 等产品已经覆盖了聊天、文献搜索、PDF 问答、写作或引用网络中的部分能力。因此本产品不以“能搜索论文、能生成文本”作为差异化卖点。

### 2.1 目标定位

> 面向中文计算机科研用户的、本地优先、证据可追溯、支持 CCF 体系的个人科研工作台。

核心差异是：用户的论文、全文、标签、检索历史、选择过的证据和草稿长期留在自己的文献库中；系统生成的文字可解释其依据、证据等级和待验证项。

### 2.2 市场能力对照

| 市场产品类型 | 常见强项 | 本产品应吸收的能力 | 本产品不应直接复制的方向 |
| --- | --- | --- | --- |
| 系统综述工具（如 Elicit） | 纳排标准、数据提取、PRISMA 工作流 | 可审计检索、筛选理由、综述证据表 | 只做一次性综述报告 |
| 深度研究工具（如 Consensus） | 多步检索、全文与引用图扩展 | 检索计划、结果复核、证据分层 | 无来源约束的长篇回答 |
| 引文智能工具（如 scite） | 支持/反驳/提及、撤稿风险 | 声明级证据与引用健康检查 | 仅输出 BibTeX 列表 |
| 引文网络工具（如 ResearchRabbit） | 关系图、订阅、相似论文 | 研究方向画像、增量提醒、引用扩展 | 社交化论文平台 |
| 写作工具（如 Paperpal） | 语言润色、投稿规范、编辑器集成 | 章节修订、格式检查、导出工作流 | 通用营销文案式生成 |

### 2.3 核心价值主张

- 论文不会因会话结束而消失：检索结果和用户操作会成为个人文献资产。
- 写作不是黑箱：引用、论文元数据、摘要或全文片段都可回溯。
- 适合中文计算机科研语境：支持 CCF A/B、常见计算机研究方向、中文任务描述与英文检索式。
- 不把“主题”“任务要求”“交付物”混为一谈：例如“调研近三年去偏推荐系统进展”中，主题是“去偏推荐系统”，调研和近三年是任务约束。

## 3. 目标用户与使用场景

### 3.1 目标用户

| 用户 | 主要问题 | 使用目标 |
| --- | --- | --- |
| 硕博研究生 | 论文多、阅读与写作割裂、难追溯引用 | 快速建立方向库、理解论文、形成可靠初稿 |
| 高校教师/科研人员 | 需要持续追踪方向、组织课题与综述 | 管理个人或课题组证据资产，发现研究空白 |
| 科研助理/实验室成员 | 需要完成文献调研和写作支撑 | 在明确边界内形成可复查调研交付物 |
| 有科研需求的工程师 | 需将技术趋势转化为研究或方案输入 | 跟踪论文、代码和技术社区动态 |

### 3.2 首要场景

1. 用户输入“调研近三年 CCF A/B 中去偏推荐系统的工作进展”，得到经过筛选的论文池、检索说明和方向总结。
2. 用户上传一篇 PDF，询问“这篇论文的核心贡献、方法假设、实验设置和局限是什么”，答案附带页码或章节证据。
3. 用户在当前项目中要求“根据文献库写一篇研究报告”或“写引言/相关工作/实验设计”，得到有结构、有真实引用、可继续编辑的草稿。
4. 用户收藏并保存论文 PDF，后续无需再次外部搜索即可复用该论文的元数据、摘要和全文片段。
5. 用户订阅已有研究方向，定期查看新论文、重要引用、开放代码、撤稿或勘误信息。

## 4. 范围与边界

### 4.1 本阶段纳入范围

- 计算机科学为主的中英文论文检索与管理。
- OpenAlex、DBLP、arXiv、Semantic Scholar、Google Scholar/合规代理等来源的适配与降级。
- CCF A/B、明确会议/期刊、年份范围和关键词约束。
- 元数据、摘要、本地 PDF、全文切片、用户标记、项目关系和写作草稿的持久化。
- 论文带读、基于证据的问答、研究方向发现、章节级写作、引用与导出。
- Kimi 为默认规划和生成模型，但模型层保持可替换。

### 4.2 明确不纳入范围

- 绕过版权、登录、付费墙或反爬机制获取受限全文。
- 保证发表、伪造实验数据、伪造作者贡献、伪造引用或伪造实验结论。
- 建设全量论文 PDF 镜像库。
- 将公众号、CSDN、知乎等技术内容当作论文写作的学术证据。
- 以规则或正则替代 LLM 对用户意图、主题和交付物的语义判断。

## 5. 产品信息架构

前端应是以项目为组织单位的科研工作台，而不是仅有一个聊天窗口。

```text
工作台
  研究协作对话与任务过程
  当前项目概览、证据状态、快捷操作

文献库
  全部论文、筛选、标签、阅读状态、本地文件状态

论文阅读
  PDF 阅读器、章节导航、原文证据、笔记、问答

写作
  章节大纲、草稿编辑、引用证据、版本历史、导出

发现
  已关注方向、最新论文、引用/代码/技术动态、订阅
```

每个页面必须共享同一个“当前项目”和“当前证据池”语义；页面切换不应取消后台任务或丢失对话输出。

## 6. 功能需求

### 6.1 项目与会话管理

项目是文献、检索、上传文件、写作草稿和方向订阅的容器。会话是项目中一段连续对话。

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| PRJ-01 | 用户可新建、切换、重命名、归档项目 | 重启服务后项目元数据仍存在 |
| PRJ-02 | 每个项目保存研究主题、研究画像、证据池、草稿和订阅 | 不同项目的论文选择和写作草稿不串库 |
| PRJ-03 | 用户可创建、切换、删除会话 | 每个会话保存消息、任务记录及上下文摘要 |
| PRJ-04 | 任务后台执行时切换页面不丢失任务状态 | 返回工作台后可见最终输出、失败原因或可重试入口 |
| PRJ-05 | 当前项目主题必须来自结构化意图中的 `normalized_topic` | 不允许把整句“调研近三年……”直接存作研究方向 |

### 6.2 对话、意图理解与 Agent 路由

系统保留自由问答入口，并由 LLM 完成意图识别。代码负责验证结构、权限、前置条件和工具执行，不通过关键词或正则重新解释用户意图。

#### 6.2.1 意图分类

第一层分类固定为以下七类，便于稳定路由和界面呈现：

| `category` | 含义 | 典型工具 |
| --- | --- | --- |
| `chat` | 自由交流、研究讨论、无需证据的问答 | `free_chat` |
| `literature_search` | 检索、筛选、调研指定方向论文 | `paper_search` |
| `evidence_qa` | 基于当前论文池或上传 PDF 提问 | `evidence_answer`、`pdf_read`、`paper_fulltext_read` |
| `document_writing` | 生成或修订有明确交付物的写作内容 | `write_document`，必要时先检索 |
| `paper_reading` | 阅读单篇上传或本地论文 | `pdf_read`、`paper_fulltext_read` |
| `document_inspection` | 检查最近生成的草稿、引用或导出文件 | `document_inspect` |
| `research_discovery` | 获取关注方向的近期进展与研究机会 | `paper_search`、发现服务 |

#### 6.2.2 结构化输出契约

LLM 必须输出 JSON。至少包括：

```json
{
  "category": "literature_search",
  "subtask": "topic_survey",
  "normalized_topic": "debiasing recommender systems",
  "display_topic": "去偏推荐系统",
  "deliverable": null,
  "evidence_scope": "fresh_and_current",
  "needs_fresh_literature": true,
  "tool_plan": ["paper_search"],
  "queries": ["debiasing recommender systems"],
  "source_queries": {"dblp": ["debiasing recommendation"]},
  "target_venues": [],
  "target_venue_ranks": ["CCF-A", "CCF-B"],
  "from_year": 2023,
  "to_year": 2026,
  "recent_years": 3,
  "cs_area": "AI",
  "requires_clarification": false,
  "clarification_question": null
}
```

规则：

- `normalized_topic` 只能是简洁研究名词短语，不含“调研”“最近三年”“写一篇”“生成”“文献库”等任务描述。
- `deliverable` 只能在写作任务中出现，例如 `report`、`survey`、`introduction`、`related_work`。
- 普通寒暄或讨论必须路由到 `free_chat`，已有论文池不能强行把它改为证据问答或检索。
- “基于当前文献库写……”应使用当前证据，不重新检索，除非用户明确要求补充最新论文。
- 模型 JSON 无效、超时或不可用时，系统不得猜测主题并自动检索；应返回可恢复的自由问答或要求用户重试。

#### 6.2.3 多意图任务

用户可以在一条消息内包含多个连续目标，例如“上传这篇论文，先总结方法，再结合近三年工作写 Related Work”。模型应输出主任务和子任务，编排器生成有限工具计划：

```text
读取上传 PDF -> 检索论文 -> 相关性复核 -> 写作
```

工具计划必须去重、限制最大步骤数，并禁止出现同一工具无限循环。每轮执行后，由状态机判断是否已有足够证据，而不是再次让模型重复选择同一个工具。

### 6.3 论文检索与筛选

#### 6.3.1 检索来源

| 来源 | 主要用途 | 约束 |
| --- | --- | --- |
| OpenAlex | 元数据、摘要、引用数、开放获取信息、增量发现 | 使用 API key 和联系邮箱；支持退避重试 |
| DBLP | 计算机会议/期刊权威书目与 venue 过滤 | 适合 CCF 会议/期刊核验；摘要需补全 |
| arXiv | 预印本、PDF 与最新工作 | 遵守速率限制和分类范围 |
| Semantic Scholar | 摘要、引用关系、字段补全 | 限流或 403 时降级，不阻塞全部任务 |
| Google Scholar/合规搜索服务 | 补充检索与手动跳转 | 仅通过合法配置的服务调用；不能依赖为唯一证据源 |

#### 6.3.2 检索流程

```text
LLM 生成主题与 1-4 个查询变体
  -> 本地库召回（标题、摘要、venue、向量）
  -> 并发调用可用外部来源
  -> 标准化与多层去重
  -> 元数据/摘要补全
  -> LLM 或混合相关性复核
  -> 过滤年份、venue、排除状态
  -> 排序、聚类、写入文献库与项目证据池
```

#### 6.3.3 筛选与排序要求

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| SRCH-01 | 支持指定研究方向、年份、会议/期刊、CCF A/B、SCI Q1-Q3、来源和开放全文状态 | 筛选条件在任务记录和结果页可见 |
| SRCH-02 | 支持主题同义表达与中英翻译扩展 | “动态推荐系统”“dynamic recommender systems”“dynamic recommendation”具有可解释的查询扩展 |
| SRCH-03 | 不以标题关键词唯一决定相关性 | 排序至少结合标题、摘要、语义相似度、venue、年份、引用和用户反馈 |
| SRCH-04 | 检索后进行主题相关性复核 | 对每篇保留/排除论文记录主题匹配理由与置信度 |
| SRCH-05 | 来源失败不应使全部任务卡住 | 显示每个来源的成功、空结果、限流、失败和重试状态 |
| SRCH-06 | 速率限制应采用退避、缓存、并发上限与熔断 | 同一来源连续失败后暂时跳过并提示，不无限重试 |
| SRCH-07 | 检索结果需要区分“论文”“元数据不完整论文”“技术社区内容” | 社区内容不可默认进入写作证据池 |

#### 6.3.4 检索质量评测

建立可版本化的检索评测集，包含至少 30 个计算机科研请求，覆盖推荐、CV、NLP、系统、安全、数据库等领域；每个请求标注主题、时间、venue 限制和人工相关论文。

初始指标：

- Top-10 相关论文精确率（Precision@10）不低于 0.7。
- Top-20 召回率（Recall@20）不低于 0.7。
- 明显跨领域误召回率低于 10%。
- 有摘要的写作候选论文比例不低于 90%。

### 6.4 个人文献库

文献库是长期资产，不是一次任务的临时搜索结果。

#### 6.4.1 存储策略

- SQLite（当前阶段）或后续 PostgreSQL 保存元数据、摘要、用户状态、项目关系和检索历史。
- `data/paper_files/` 保存用户上传、下载或导入的 PDF 原文。
- `data/paper_texts/` 保存解析后的全文结构与 chunk。
- 数据库只保存文件路径、校验和与状态，不能保存 PDF 二进制或完整大文本。

#### 6.4.2 论文资产字段

| 分类 | 字段 |
| --- | --- |
| 识别 | `paper_id`、`title`、`doi`、`arxiv_id`、规范化标题 |
| 书目 | `authors`、`year`、`venue`、`volume`、`pages`、`publication_type` |
| 内容 | `abstract`、`keywords`、`fields_of_study`、`citation_count`、`reference_count` |
| 来源 | `sources`、`source_url`、`pdf_url`、`open_access_url`、`retrieved_at` |
| 本地文件 | `local_pdf_path`、`local_text_path`、`fulltext_status`、`fulltext_sha256`、`fulltext_error` |
| 用户资产 | `reading_status`、`importance`、`tags`、`notes`、`excluded`、`exclusion_reason` |
| 项目使用 | `project_id`、`relevance_score`、`selection_status`、`used_in_sections` |

#### 6.4.3 去重与合并

入库按以下优先级识别相同论文：规范化 DOI、去版本 arXiv ID、规范化标题、标题+年份+前三作者。合并后：

- 保留更完整、更长且可信的摘要。
- 合并所有来源与检索历史，来源必须是结构化关系表，不能用重复拼接字符串。
- 保留最大引用数、可用 PDF 路径、开放全文链接和用户状态。
- 用户的标签、笔记、已读状态、核心标记、排除状态不能被外部刷新覆盖。

#### 6.4.4 文献库交互

- 支持搜索、筛选、排序、批量选择、加入/移出当前项目、标记核心、排除、添加标签和笔记。
- 支持“打开本地文献库文件夹”“批量导入 PDF”“自动匹配 PDF”“下载开放全文”。
- 下载失败必须展示具体原因：无开放链接、下载被拒、文件解析失败、链接失效或网络错误。
- PDF 自动匹配优先使用 DOI、arXiv ID、文件内标题、文件名和标题相似度；无法高置信匹配时要求用户确认，不能绑定到错误论文。

### 6.5 PDF 阅读与全文证据

#### 6.5.1 阅读能力

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| READ-01 | 支持上传单个或批量 PDF 并保存到个人文献库 | 上传成功后可见本地位置、页数、解析状态与匹配论文 |
| READ-02 | 提取标题、摘要、章节、段落、引用、表格/图注的可用文本 | 结构不可识别时明确降级为页级文本 |
| READ-03 | 用户可对单篇论文提问 | 回答附带论文名、页码/章节和短原文证据 |
| READ-04 | 系统可从本地全文中挑选相关 chunk 供问答和写作使用 | 不把整篇 PDF 原文直接塞进模型上下文 |
| READ-05 | 无法读取扫描版或加密 PDF 时给出明确状态 | 不声称“已阅读全文” |

#### 6.5.2 证据分级

写作和问答中的证据必须标记来源等级：

| 等级 | 来源 | 可支持的内容 |
| --- | --- | --- |
| A | 本地 PDF 全文、可定位页码 | 方法、实验、指标、局限、精确结论 |
| B | 可信外部摘要与元数据 | 研究定位、任务、宏观贡献 |
| C | 标题、venue、年份、引用数 | 仅可用于书目定位，不能支持技术细节 |
| D | 技术社区/RSS | 仅用于发现和工程动态，不能做学术事实证据 |

### 6.6 证据问答与引用健康

证据问答是“使用已有证据回答”，不是隐式搜索或一般聊天。

- 回答应区分：论文明确陈述、跨论文综合推断、模型建议、待验证事项。
- 没有足够证据时，明确说明缺少摘要或全文，并建议补充论文或发起检索。
- 引用记录至少包含 `paper_id`、citation key、来源 URL、证据等级、支撑片段和页码/章节（如有）。
- 后续阶段支持引用关系的 `supporting`、`contrasting`、`mentioning` 分类，以及撤稿、勘误、表达关注等健康检查。

### 6.7 证据化写作

写作是核心能力，不是 Related Work 的单一模板。统一的 `academic-writing` Skill 负责写作导航，并根据交付物选择资源文件和质量标准。

#### 6.7.1 支持的写作交付物

| `deliverable` | 交付物 | 主要输入 | 不允许生成的内容 |
| --- | --- | --- | --- |
| `outline` | 大纲与章节计划 | 主题、证据池、目标格式 | 没有依据的细节结论 |
| `report` | 研究报告 | 方向、论文池、分析目标 | 虚构研究发现 |
| `survey` | 综述 | 纳入论文、分类维度、范围 | 把未纳入论文写成已调研 |
| `related_work` | 相关工作 | 当前工作定位、相关论文 | 把论文列表拼成正文 |
| `introduction` | 引言 | 研究问题、问题背景、已有缺口 | 虚构本文贡献或实验结果 |
| `method_section` | 方法设计/方法草案 | 用户提供的方法、已有证据 | 编造已实现模型或公式结果 |
| `experiment_section` | 实验设计 | 任务、数据集、基线和限制 | 编造实验数值和显著性 |
| `summary` | 文献/章节总结 | 单篇或多篇证据 | 超出原文的技术结论 |
| `bibliography` | BibTeX/参考文献 | 已选论文 | 生成不存在的书目 |
| `general` | 其他学术文本 | 用户明确要求 | 超出证据边界的事实 |

#### 6.7.2 写作工作流

```text
识别写作目标、受众、语言、篇幅和目标 venue
  -> 选择当前项目证据或明确补充检索
  -> 检查证据覆盖与全文可用性
  -> 生成/确认大纲
  -> 按章节生成草稿
  -> 绑定句子/段落与 citation key、paper_id、证据等级
  -> 引用完整性、重复性、结构和格式检查
  -> 保存版本并提供预览、编辑与导出
```

#### 6.7.3 写作质量要求

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| WRITE-01 | 不将所有写作请求套入 Related Work 模板 | “写研究报告”“写实验设计”“写摘要”生成对应结构 |
| WRITE-02 | 每个交付物具有独立结构约束和 Prompt 资源 | 资源通过统一写作导航加载，不能散落在代码分支中 |
| WRITE-03 | 写作优先选择高证据等级论文 | 全文可用论文优先用于技术细节；仅标题论文不用于具体结论 |
| WRITE-04 | 用户可指定中文/英文、字数、学术风格、目标会议和引用样式 | 设置写入草稿元数据并影响生成结果 |
| WRITE-05 | 支持扩写、缩写、改写、润色、审稿意见修改和局部重写 | 局部操作不覆盖未选内容，并生成新版本 |
| WRITE-06 | 生成前后执行引用与事实检查 | 不存在的 citation key、未在证据池的论文、无证据事实应被标记或阻止导出 |
| WRITE-07 | 方法与实验草稿明确区分“已有证据”“作者待补信息”“建议” | 不得生成虚构数据集结果、消融表或显著性结论 |
| WRITE-08 | 草稿必须保存版本、差异和质量报告 | 用户可比较、恢复历史版本 |

#### 6.7.4 写作编辑器

- 中央区域为可编辑 Markdown/富文本正文；渲染后的 Markdown、LaTeX、表格和引用必须可读。
- 右侧显示当前段落的引用、证据片段、证据等级和质量警告。
- 点击引用跳转到论文详情或 PDF 页码。
- 提供章节树、版本历史、内容统计、缺失引用提醒和导出菜单。
- 输出与思考过程分离：执行时以对话流展示简洁的可见任务状态；结果出现后任务状态自动折叠，不应占据正文区域。

#### 6.7.5 导出与互操作

必须支持 Markdown、BibTeX、RIS、CSL-JSON、DOCX、LaTeX。后续支持 Zotero 导入/导出和 Overleaf 项目同步。导出前运行引用检查，导出包包含正文、参考文献和可选 claim map。

### 6.8 发现与研究机会

发现模块不应只依据上一句对话，而要根据用户长期的项目、已选论文、标签、查询和阅读行为形成可解释的研究画像。

#### 6.8.1 发现输入

- 项目 `normalized_topic` 和子方向。
- 最近检索和用户确认的相关论文。
- 核心/收藏/已读论文、标签、笔记和写作章节。
- 用户明确订阅的 venue、作者、关键词、时间范围。

#### 6.8.2 输出内容

- 最新论文增量：按来源、年份、venue 和相关性分类。
- 重要引用变化：高影响新论文、被频繁引用的经典工作、可能撤稿/勘误风险。
- 开放代码、数据集和技术动态：与论文证据明确分区显示。
- 待验证研究机会：根据不足的证据覆盖、未充分对比的设置、近期方向交叉生成；必须标为“建议”，不是事实结论。

#### 6.8.3 订阅与任务

- 支持手动刷新、定期后台刷新、失败重试和“上次更新”记录。
- 每条推荐说明推荐原因：与哪一主题、论文、关键词或 venue 的关联。
- 支持 OpenAlex、DBLP、arXiv；RSSHub/RSS 仅作为公众号、CSDN、知乎等工程社区动态补充。

## 7. 前端需求

### 7.1 通用体验

- 桌面优先，同时保证常见笔记本分辨率下内容不重叠。
- 对话历史在独立可滚动容器中滚动；输入区始终固定在工作区底部可见。
- 页面整体不应因聊天内容变长而被迫滚动到输入框之外。
- 状态、错误、空结果和完成结果必须明确区分。
- 所有长文本、文献标题和路径支持截断、悬停完整提示和可点击查看。

### 7.2 流式任务反馈

借鉴成熟 Agent 的交互方式，但只显示用户有价值的过程摘要，不暴露模型私有思维链。

```text
用户消息
  -> 正在理解任务
  -> 已识别：检索 / 写作 / 阅读等计划
  -> 正在调用：本地库、OpenAlex、DBLP 等
  -> 正在筛选与核验
  -> 输出结果
```

要求：

- 服务端使用可恢复的 SSE 或等价事件流，事件有任务 ID、阶段、内容、时间戳和最终状态。
- 前端在收到最终 `answer` 或 `document` 事件后展示普通助手消息，并折叠过程信息。
- 页面切换后重新订阅任务事件或从任务存储补齐历史，不能出现“已完成但对话框没有结果”。
- 任务失败显示可读错误、失败来源和重试操作；不只显示 `Failed to fetch`。

### 7.3 页面级要求

| 页面 | 关键组件 |
| --- | --- |
| 工作台 | 对话流、任务折叠卡、输入框、当前项目摘要、证据状态 |
| 文献库 | 表格/列表、筛选器、批量操作、本地 PDF 状态、下载/打开/匹配按钮 |
| 论文阅读 | PDF 预览、目录、问题输入、证据引用、笔记和加入写作按钮 |
| 写作 | 大纲、编辑器、证据侧栏、版本历史、质量报告、导出 |
| 发现 | 关注主题、来源状态、增量论文、订阅、研究机会与社区动态 |

## 8. 后端与 Agent 架构

### 8.1 分层原则

```text
interfaces
  Web / CLI / API 协议与流式事件
       -> core
          请求上下文、Agent 编排、状态机、排序、全文解析、写作质量控制
       -> tools
          外部论文源、LLM、PDF 下载、导出等受控能力
       -> skills
          版本化工作流提示词与写作资源
       -> storage
          SQLite/数据库、文件资产、任务和会话持久化
```

当前代码中的 `PaperToolRegistry` 继续作为 Tool 的唯一契约来源，`PaperSkillCatalog` 继续作为 Skill 导航。外部模型只能选择定义过的能力，不能直接执行 Python、任意 URL 或任意文件操作。

### 8.2 Tool 要求

| Tool | 输入 | 输出 | 前置条件 |
| --- | --- | --- | --- |
| `paper_search` | 结构化主题、查询、来源、时间、venue | 论文候选、来源统计、过滤理由 | 有有效 `normalized_topic` |
| `pdf_read` | 上传 PDF 与问题 | 相关页/章节、片段、答案 | 会话已上传 PDF |
| `paper_fulltext_read` | 论文标识与问题 | 本地全文片段、页码、答案 | 有本地或可合法获取的全文 |
| `evidence_answer` | 问题与证据范围 | 带引用的答案、证据不足说明 | 论文池或 PDF 存在 |
| `write_document` | 交付物、写作配置、证据范围 | 草稿、引用、质量报告、版本 | 有证据或计划中先检索 |
| `document_inspect` | 草稿/导出文件与核验项 | 完整性、引用、结构问题 | 有生成文档 |
| `free_chat` | 消息与会话摘要 | 普通对话答复 | 无 |

### 8.3 Skill 要求

Skill 不直接执行代码。它定义输入、步骤、质量规则、输出格式和失败时的降级策略。

```text
skills/definitions/
  literature-research/
  pdf-reading/
  evidence-grounding/
  research-discovery/
  academic-writing/
    SKILL.md                  # 统一写作导航
    resources/
      writing-routing.md
      markdown-contract.md
      report.md
      survey.md
      related-work.md
      introduction.md
      method.md
      experiment.md
      summary.md
      outline.md
      bibliography.md
      general.md
```

`academic-writing/SKILL.md` 必须先导航到 `writing-routing.md`，再选择对应资源。每个资源都需包含：适用场景、必须输入、推荐结构、证据要求、禁止事项、引用规则、质量检查和输出格式。

### 8.4 任务状态机

每个任务具有有限状态，避免重复工具循环：

```text
queued -> planning -> running -> validating -> completed
                         |             |
                         v             v
                       retrying ------> failed
```

- 同一工具连续执行的最大次数可配置；达到上限时进入 `failed` 或等待用户确认。
- 搜索、下载、全文解析和生成均为可独立重试的子任务。
- 任务状态、输入摘要、工具调用摘要、错误和最终输出必须持久化。

## 9. 数据模型与接口要求

### 9.1 核心实体

| 实体 | 核心职责 |
| --- | --- |
| `projects` | 研究主题、画像、设置、订阅与归档状态 |
| `conversations` / `messages` | 多轮对话、上下文摘要和输出 |
| `papers` | 规范化论文元数据与本地资产状态 |
| `paper_sources` | 一篇论文对应的多来源 URL、外部 ID 和抓取时间 |
| `paper_queries` | 论文为何因何查询进入文献库 |
| `project_papers` | 项目对论文的相关度、纳入/排除、章节使用状态 |
| `documents` / `draft_versions` | 草稿、版本、写作配置、质量报告和导出关系 |
| `evidence_chunks` | PDF/摘要的文本块、位置、哈希和向量索引 |
| `claims` / `claim_evidence` | 草稿中的声明与支撑论文/片段的映射 |
| `jobs` / `job_events` | 后台任务、事件流重放、失败和重试 |
| `subscriptions` / `discovery_items` | 方向订阅与增量发现结果 |

### 9.2 关键 API 契约

| 接口 | 说明 |
| --- | --- |
| `POST /api/projects` | 创建项目，返回项目对象 |
| `GET /api/projects/{id}` | 获取项目概览、论文与草稿统计 |
| `POST /api/conversations/{id}/messages` | 提交消息，返回 `job_id` |
| `GET /api/jobs/{id}/events` | SSE 任务流，含 `stage`、`message`、`payload`、`status` |
| `POST /api/projects/{id}/searches` | 运行结构化检索 |
| `GET /api/projects/{id}/papers` | 获取项目论文池，支持过滤和分页 |
| `PATCH /api/papers/{id}` | 更新标签、重要性、阅读状态、排除原因等 |
| `POST /api/papers/import` | 批量导入或匹配本地 PDF |
| `POST /api/papers/{id}/fulltext` | 尝试下载/解析合规开放全文 |
| `POST /api/projects/{id}/documents` | 创建写作任务 |
| `PATCH /api/documents/{id}` | 保存用户编辑，创建新版本 |
| `POST /api/documents/{id}/exports` | 导出 Markdown/LaTeX/DOCX/BibTeX 等 |
| `POST /api/projects/{id}/discoveries/refresh` | 刷新发现模块 |

接口响应应使用稳定 ID，不以文件名作为主标识。错误响应至少包含 `code`、`message`、`retryable`、`source` 和可选 `details`。

## 10. 非功能需求

### 10.1 性能与可靠性

- 简单聊天在 Kimi 可用时应尽量走轻量路径；不能因全量检索或复杂规划阻塞 `hello`。
- 外部来源检索应并发、超时隔离、缓存优先；一个来源失败不阻断其他来源与已缓存结果。
- 任务可取消、重试、恢复，并在服务重启后根据状态恢复或明确标记中断。
- 1 万篇论文的元数据/摘要在 SQLite 中应保持可交互，普通列表与筛选目标小于 1 秒。
- 解析 25 MB 以内普通 PDF 的成功率目标不低于 90%；失败必须可解释。

### 10.2 安全、隐私与合规

- API key 仅从环境变量或本地配置读取，日志和前端不得回显密钥。
- 用户上传 PDF 默认仅保存在本地工作区；没有明确授权不得上传第三方。
- 遵守数据源 API、robots、版权和开放获取约束。
- 已删除项目或文件采取可恢复删除策略，并说明本地文件是否仍保留。
- LLM 提示词与工具输入需防范上传论文、网页元数据或外部文本中的提示注入；外部内容仅作为数据，不作为系统指令。

### 10.3 可观测性与评估

- 记录每次任务的模型、耗时、工具链、来源调用、缓存命中、错误和重试。
- 记录写作的证据覆盖率、无效引用数、使用全文/摘要/标题的比例。
- 建立回归测试集：意图路由、主题抽取、检索相关性、去重、全文定位、写作结构和引用一致性。
- 对 Prompt、模型和排序策略做版本标记，支持问题复现。

## 11. 里程碑与优先级

### P0：可信输入与核心写作闭环

1. 重构意图契约与有限状态机，解决主题被识别成整句任务、检索被误路由为自由聊天、工具循环等问题。
2. 建立检索评测集；接入本地 FTS5/BM25、向量召回和融合排序；检索后进行相关性复核。
3. 完善多源并发、限流退避、熔断和可读失败反馈。
4. 重构统一写作 Skill：各章节独立资源、真实内容生成、证据等级和引用检查。
5. 实现项目、会话、草稿和任务的后端持久化，替代仅依赖浏览器状态的方案。

### P1：深度阅读与可编辑写作工作流

1. 完善 PDF 结构解析、全文 chunk、页码证据、批量导入与自动匹配。
2. 完善文献库用户状态、项目选文、重复合并和来源规范化。
3. 上线章节编辑器、草稿版本、局部修订、质量报告与 DOCX/LaTeX/引用格式导出。
4. 完成系统综述支持：纳排标准、筛选记录、证据表和 PRISMA 导出。

### P2：长期研究画像与方向发现

1. 基于项目、选文、标签、阅读与写作行为建立方向画像。
2. 增加增量论文订阅、引用/撤稿/代码/会议截止日期提醒。
3. 引入 citation graph、研究缺口分析、论文聚类和可解释推荐。
4. 支持本地部署备份、团队共享库、Zotero/Overleaf 集成。

## 12. 发布验收标准

版本达到“可用于真实科研工作”的最低条件：

- 用户输入“调研近三年去偏推荐系统”后，项目方向显示为“去偏推荐系统”，而非完整请求句。
- 该请求路由到检索，普通寒暄路由到自由问答；两者均有可见最终输出。
- 检索结果至少显示来源、年份、venue、摘要状态、相关性理由、全文状态及失败来源说明。
- 用户选定论文后，重启服务仍能在文献库与项目中看到它们。
- 上传或导入 PDF 后可自动或半自动正确绑定论文，并可从本地文件路径阅读。
- 基于当前文献库写研究报告、综述、引言、Related Work、方法/实验设计时，生成结构与任务匹配，不能只输出标题或套用 Related Work。
- 所有输出引用都来自当前证据池；无证据技术细节会被标记为待验证，不会伪装为论文结论。
- 写作页面可查看、编辑、版本化并导出正文和参考文献。
- 任务过程在对话流内可见，完成后折叠；页面切换和服务短暂重启不应让最终输出丢失。
